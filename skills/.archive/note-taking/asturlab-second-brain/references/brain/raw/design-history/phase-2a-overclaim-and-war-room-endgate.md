# Phase 2a overclaim and War Room end-gate correction

Session lesson: when building the AsturLAB second brain, do not let War Room OS urgency pollute the brain foundation.

## Correct answer to the War Room sequencing question

If War Room is moved to the end, second-brain build quality should not suffer. It should usually improve because the build can stay focused on source integrity, compiled pages, retrieval proof, E-compress, index/log/processed consistency, and Dream validation.

The cost is operational cadence speed. War Room produces strategy, accountability, scorecards, and cadence. Delaying it delays those benefits. That is separate from the quality of the brain build.

## Phase naming discipline

Do not call Phase 2 complete after only a manual ingest/capture slice.

Use these labels:

- Phase 2a: manual ingest/capture proof.
- Phase 2b: genuinely proven retrieval/query flow.
- Phase 2c: deterministic E-compress/distillation demonstration.
- Phase 3: manual Dream Sequence health pass.

If a doc, test, or final reply claims a phase is done, verify that the named operation actually happened.

## Review discipline

If the session contract says high-effort work requires Claude Code Opus in tmux with a file-output contract, run the Opus review before calling the slice done.

Do not wait for Rawan to ask where Opus was.

## Acceptance-test discipline

Presence checks are not operational proof.

A real query test must prove retrieval is non-tautological: read the index, search compiled pages/raw pages, read matching pages, cite results, and identify compiled-date or source-status warnings.

A real Dream test must audit health: broken links, orphan pages, duplicate claims, stale pages, unreviewed pages, source pointer gaps, index completeness, and processed-ledger consistency.

A real E-compress test must demonstrate a deterministic compression/distillation step, not merely describe it.

## War Room artifact handling

If War Room files were created due to scope bleed and Rawan says he wants to start War Room fresh later, identify committed versus uncommitted artifacts first. Ask for explicit confirmation before destructive removal. After confirmation, remove the mistaken active-tree files and continue the brain build.
